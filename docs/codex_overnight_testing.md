# Codex Overnight Testing Playbook

这是一个用于 **让 Codex 在一个晚上里按阶段跑复杂/大型项目** 的测试方法模板。

## 0. 目标

不要把“做一个大项目”作为一个单独的指令丢给 Codex。  
正确做法是把它变成：

> 一个可验证、可回滚、可分阶段推进的工程代理测试。

测试焦点不是“生成多少代码”，而是：

- Codex 是否能持续保持结构；
- Codex 是否能按阶段推进；
- Codex 是否能在每一步内通过测试；
- Codex 是否会在失败时缩小范围，而不是乱改；
- Codex 是否能稳定产生可提交的 diff。

---

## 1. 开始前的准备

在启动夜间测试前，先确认这些文件存在：

```text
README.md
AGENTS.md
PLAN.md
Makefile
src/
tests/
```

至少准备好：

1. 一个可重复执行的快速测试命令：
   ```bash
   make test
   ```
2. 一个明确的构建或运行命令：
   ```bash
   make run
   ```
3. 一个干净的 Git 工作区：
   ```bash
   git status --short
   ```

如果 `make test` 本身很慢，就先把它优化成分层形式，例如：

```bash
make unit
make integration
make test
```

夜间测试不应该依赖一个需要几十分钟才会给出反馈的总测试命令。

---

## 2. 任务拆分原则

夜间跑复杂项目时，不要用下面这种 prompt：

> 帮我写一个大项目。

要改成这样：

> 按 `PLAN.md` 的 phase-02 实现 core service，最小范围修改，完成后跑 `make test`。

推荐的阶段结构：

```text
phase-01  项目骨架 / 目录结构 / 初始化
phase-02  核心接口 / 类型定义 / 配置加载
phase-03  数据层或存储层
phase-04  服务层 / 业务逻辑
phase-05  CLI / API / 前端入口
phase-06  测试补齐
phase-07  性能 / 并发 / 通信基线
phase-08  文档整理 / README / 运行脚本
```

每个阶段都应该满足：

1. 范围小；
2. 有明确验收标准；
3. 可以独立编译；
4. 可以独立测试；
5. 可以独立提交。

---

## 3. 推荐的夜间任务循环

可以用一个简单的任务列表驱动 Codex。

```bash
while read -r task; do
  codex run "$task"
done <<'EOF'
按 PLAN.md 实现 phase-01 项目骨架
按 PLAN.md 实现 phase-02 核心接口
按 PLAN.md 实现 phase-03 数据层
按 PLAN.md 实现 phase-04 服务层
按 PLAN.md 实现 phase-05 CLI
按 PLAN.md 实现 phase-06 测试补齐
按 PLAN.md 实现 phase-07 通信或性能基线
按 PLAN.md 实现 phase-08 文档与运行脚本
EOF
```

这里重点是：

- 外层负责控制“下一个阶段”；
- 内层负责正常的 Codex 工作流；
- 每个阶段完成后都回到 Git 状态；
- 如果某个阶段失败，不应该继续强行进入下一个阶段。

---

## 4. 每个阶段的标准验收

每个 phase 都按这个顺序检查：

### 4.1 修改前

先确认：

```bash
git status --short
make test
```

如果当前测试已经是失败的，先把失败原因修复，再开始新阶段。

### 4.2 实现时

要求 Codex：

1. 不要一次性大改；
2. 先读相关文件；
3. 只改当前 phase 相关的文件；
4. 每个修改都写成最小可回滚的 diff；
5. 如果发现需要新依赖，先说明，不直接引入。

### 4.3 实现后

跑：

```bash
make unit
make integration
make test
```

如果测试失败，要求 Codex：

1. 先解释失败点；
2. 不要直接换实现；
3. 不要因为测试不好过而去改测试；
4. 只有确认测试本身写错了，才允许修改测试。

### 4.4 提交

每个成功的 phase 做一个独立提交：

```bash
git add -A
git commit -m "Phase 0X: <短描述>"
```

如果 push 有权限问题，可以先只做本地提交。

---

## 5. 中断后的恢复方法

夜间测试经常会被失败卡住。

推荐使用下面这段固定恢复 prompt：

```text
先不要继续实现新 phase。
运行 git status 和 make test。
根据当前失败信息定位根因。
只修与当前 phase 相关的问题。
修复后重新跑 make test。
如果测试通过，把当前 phase 标记为完成。
如果失败超过 3 次，停下并给出结论。
```

这段 prompt 的作用是防止 Codex 在失败后继续叠代码。

---

## 6. 失败处理策略

遇到下面情况时，应该停下而不是继续：

1. `make test` 连续 3 次失败；
2. 某个 phase 的修改范围明显扩大；
3. Codex 开始改不相关文件；
4. 已经无法用一个 commit 描述当前变更；
5. 测试耗时突然大幅增加；
6. 构建环境本身不稳定。

停下来后，只做一件事：

> 固定当前最小 diff，写清楚卡住原因和下一步。

这比继续盲跑更有价值。

---

## 7. 推荐的单次迭代节奏

一个健康的长跑循环大概是这样：

```text
读 PLAN
读相关源码
设计小 diff
实现
跑单测
跑集成测试
确认 diff 范围
commit
进入下一个 phase
```

如果发现脱离这个节奏，就把它拉回来。

---

## 8. 夜间测试成功标准

一晚结束时，不是看代码量，而是看这四件事：

1. `make test` 是否全部通过；
2. 每个 phase 是否都有独立提交；
3. 是否还有清晰的下一步；
4. `README.md` 是否能解释今天产出如何运行。

理想的结束状态是：

```text
新能力：可运行
测试：通过
提交：每个 phase 一个
文档：能说明如何跑
已知问题：有记录
下一步：有明确 phase
```

---

## 9. 快速启动清单

启动前只做这四件事：

```bash
git status --short
make test
cat PLAN.md
cat AGENTS.md
```

然后按 phase 一个一个推进。

不要让 Codex 做下面这些事：

- 一次生成整个项目；
-跳过测试直接进入下一个功能；
-在失败后继续叠补丁；
-为了“完成感”去改无关文件。

---

## 10. 一句话原则

小型可验证的一步步推进，比一次生成一大段代码更快、更稳，也更适合晚上长跑。

---

## 11. 参考：GitHub 高星 skill 中的可复用范式

这次夜间测试可以参考一些公开 agent-skill 仓库的常见模式，而不是照搬仓库本身。

### 值得参照的三类仓库

| 类型 | 价值 |
| --- | --- |
| `obra/superpowers` | 提供 agent 驱动开发的理论框架和工作流；不只是写代码，还强调先定 spec，再 plan，后执行 |
| `anthropics/skills` | 提供 skill 组织结构：干净的任务说明 + 可复用的行为模板，适合我们组织长跑测试 |
| `composio-community/awesome-codex-skills` | 汇集 Codex CLI / API 相关的实用 skill；适合灵感，不必全装 |

上面不是“clone 后直接用”，而是提炼出几个适合我们夜间长跑的工作方式。

### 提炼出的核心范式

1. **Verification 先于宣告**
   - 写完代码不等于完成；
   - 先确认能跑、能测、能构建；
   - 如果没有可验证证据，就不能 claim "done"。

2. **限制每次任务范围**
   - 每次只处理一个 phase / 一个文件范围；
   - 避免一次大改；
   - 每个 phase 之间都要有检查点。

3. **Plan 必须可执行**
   - 不是“做服务层”这种大词；
   - 应该变成“改这几个文件，跑这条测试，验收标准是什么”。

4. **失败先找根因，不急着 patch**
   - 对于任何出错信息，先做根因分析；
   - 不要在第一反应直接改实现；
   - 如果根因不明，先记录和降级目标。

5. **让 agent 提前回问**
   - 如果某个 phase 前置条件不满足，先停下问，不要强行展开；
   - 夜间长跑中反复问一次的成本，远低于盲跑一晚。

6. **Review 采用小步走**
   - 每 phase 结束后回看文件；
   - 看 diff，看测试，看文档；
   - 再决定是否进入下一个阶段。

### 这给我们的具体启示

这份 playbook 的运行核心其实和这些高星 skill 是一个思路：

```text
spec → plan → 验证式小步推进 → 记录状态 → 自检 → commit
```

和直接拿着 skill loudly宣读相比，重要的是把这套结构变成你下一次 prompt 的默认动作。
